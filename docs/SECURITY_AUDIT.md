# Аудит безопасности — Warborn (Project: Minecraft)

**Дата:** 4 марта 2026  
**Объект:** Next.js-приложение (аутентификация, админ-панель, GML Launcher API, Minecraft API).

---

## Внесённые исправления (по результатам аудита)

- **JWT:** добавлен `lib/jwt.ts` с `getJwtSecret()` — без fallback; при отсутствии `JWT_SECRET` приложение выбрасывает ошибку. Все маршруты переведены на использование этой функции.
- **Админ-проверка:** `lib/admin-auth.ts` теперь возвращает `{ valid, userId? }` и проверяет роль по БД. Эндпоинты `/api/admin/users/[id]` и `/api/admin/users/[id]/ban` используют общий `verifyAdmin()` из `lib/admin-auth.ts`.
- **RCON в коде:** из `update_config.ts` убран жёстко прописанный пароль. Скрипт берёт `RCON_PORT` и `RCON_PASSWORD` из переменных окружения (при отсутствии пароль не задаётся).
- **Куки:** для `cf_verified` в продакшене установлено `secure: true`.
- **Заголовки:** в `next.config.ts` добавлены `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`.

**Что остаётся сделать:** rate limiting для login/register/GML auth, обязательный `GML_AUTH_SECRET` в прод, валидация email/паролей и настроек — см. план ниже.

## Критические уязвимости

### 1. Fallback JWT-секрета в коде

**Файлы:** `lib/admin-auth.ts`, `app/api/auth/login/route.ts`, `app/api/auth/me/route.ts`, `app/api/profile/get/route.ts`, `app/api/admin/users/[id]/route.ts`, `app/api/admin/users/[id]/ban/route.ts`, `app/dashboard/layout.tsx`

```ts
const JWT_SECRET = process.env.JWT_SECRET || 'warborn-secret-key';
```

Если `JWT_SECRET` не задан (или не подхватился), используется предсказуемый ключ. Злоумышленник может подписывать произвольные JWT (в т.ч. с `role: 'ADMIN'`) и получать полный доступ.

**Рекомендация:** не использовать fallback. При старте приложения проверять наличие `JWT_SECRET` и падать с явной ошибкой, если переменная отсутствует.

---

### 2. Жёстко прописанный RCON-пароль в репозитории

**Файл:** `update_config.ts`

```ts
rconPassword: '3475247'
```

Пароль RCON в коде даёт полный доступ к управлению Minecraft-сервером. При попадании репозитория в открытый доступ или утечке кода пароль считается скомпрометированным.

**Рекомендация:** убрать пароль из кода. Брать значения из переменных окружения или из уже сохранённой в БД конфигурации; скрипт обновления конфига не должен содержать секретов.

---

### 3. Эндпоинт `/api/admin/users/[id]/ban` не проверяет роль по БД

**Файл:** `app/api/admin/users/[id]/ban/route.ts`

Используется локальная функция `verifyAdmin()`, которая только проверяет JWT и поле `role` в токене. Роль в базе данных не проверяется.

Последствия:

- Выданный когда-то токен с `role: 'ADMIN'` продолжит работать для бана даже после снятия прав в БД (до истечения срока жизни токена).
- При компрометации JWT-секрета возможна выдача самоподписанного токена с `role: 'ADMIN'` и доступ к бану без проверки по БД.

**Рекомендация:** использовать общую проверку админа из `lib/admin-auth.ts` (которая сверяет роль по БД), как в остальных админ-эндпоинтах.

---

### 4. GML Auth без ограничения запросов и опциональный секрет

**Файл:** `app/api/gml/auth/route.ts`

- Если `GML_AUTH_SECRET` не задан, эндпоинт доступен с любого источника и допускает перебор паролей по логину.
- Нет rate limiting — возможны брутфорс и перегрузка сервиса.

**Рекомендация:** в продакшене обязательно задавать `GML_AUTH_SECRET` и проверять заголовок `x-gml-auth-secret`. Добавить rate limiting по IP (и при необходимости по логину) для всех эндпоинтов входа (в т.ч. GML).

## Высокий риск

### 5. Отсутствие rate limiting

Эндпоинты входа и регистрации не ограничивают частоту запросов:

- `/api/auth/login`
- `/api/auth/register`
- `/api/auth/challenge`
- `/api/gml/auth`

Возможны: брутфорс паролей, перебор учётных записей, DoS.

**Рекомендация:** ввести rate limiting (по IP и, где уместно, по логину/email), например через middleware или отдельный слой (Redis + счётчики, или готовое решение для Next.js).

---

### 6. Куки `cf_verified` с `secure: false`

**Файл:** `app/api/auth/challenge/route.ts`

```ts
secure: false, // Set to true in production if HTTPS
```

При работе по HTTP кука может передаваться по незашифрованному каналу и быть перехвачена (MITM).

**Рекомендация:** в продакшене всегда устанавливать `secure: true` при наличии HTTPS (например, по `NODE_ENV === 'production'` или отдельной переменной).

---

### 7. Отсутствие заголовков безопасности

В ответах приложения не выставляются:

- `X-Frame-Options` (защита от clickjacking)
- `X-Content-Type-Options: nosniff`
- `Content-Security-Policy` (CSP)
- `Strict-Transport-Security` (HSTS при HTTPS)
- `Referrer-Policy`

**Рекомендация:** добавить эти заголовки глобально (например, в `next.config.ts` или в middleware).

---

### 8. Долгий срок жизни JWT (30 дней)

**Файл:** `app/api/auth/login/route.ts`

`maxAge: 60 * 60 * 24 * 30` — токен действителен 30 дней. При утечке токена окно компрометации велико; отзыв возможен только при смене секрета (инвалидация всех сессий).

**Рекомендация:** сократить срок жизни access-токена (например, 1–24 часа) и при необходимости ввести refresh-токены с отдельным, более длинным сроком и хранением в БД для возможности отзыва.

## Средний риск

### 9. Валидация email при регистрации

**Файл:** `app/api/auth/register/route.ts`

Проверяется только наличие поля. Формат email не валидируется — возможны некорректные или одноразовые адреса.

**Рекомендация:** проверять формат (регулярное выражение или библиотека вроде validator/email-validator) и при необходимости — домен/диспозабл-листы.

---

### 10. Слабая политика паролей

Требуется только длина не менее 6 символов. Нет требований к сложности (заглавные, цифры, спецсимволы).

**Рекомендация:** ввести минимальную сложность (длина 8+, комбинация символов) и при необходимости проверку по списку утёкших паролей (например, haveibeenpwned).

---

### 11. Конфигурация в БД без санитизации

**Файл:** `app/api/admin/settings/route.ts`

Поля `serverIp`, `rconPort`, `rconPassword` и т.д. сохраняются из тела запроса без явной валидации (типы, длина, допустимые символы). Риск — некорректные или чрезмерно длинные значения, возможные проблемы при дальнейшем использовании (например, в RCON).

**Рекомендация:** валидировать все поля (Zod/йоп и т.п.): тип, длина, формат IP/порта, допустимые символы для пароля.

---

## Низкий риск / позитивные моменты

### 12. Секреты в .env и .gitignore

`.env*` указан в `.gitignore` — файлы с секретами не должны попадать в репозиторий. Следует убедиться, что в истории git нет коммитов с `.env` и что в продакшене используются переменные окружения, а не файлы из репо.

### 13. Запросы к БД

Использование Prisma и параметризованных запросов (`$queryRaw` с плейсхолдерами) снижает риск SQL-инъекций. Сырая конкатенация SQL не обнаружена.

### 14. Пароли и куки

- Пароли хранятся в виде хеша bcrypt.
- В ответах не отдаётся поле `password` (исключается из объекта пользователя).
- Куки `auth_token` и `cf_verified` помечены `httpOnly`, `sameSite: 'lax'`.
